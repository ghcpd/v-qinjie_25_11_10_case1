## 3) Repairs I applied (summary and rationale)
I replaced unsafe and insecure patterns with safer alternatives:

- Removed hardcoded secret
  - Before: `DB_PASSWORD = "root_password123"`
  - After: code now reads database password from the environment using `os.environ.get("DB_PASSWORD")`.
  - Rationale: prevents secrets from being stored in source; use environment variables or a secrets manager. The patched code raises an error if the environment variable is missing (fail-fast).

- Removed direct usage of exec() for executing user-supplied scripts
  - Before: reading a file and calling `exec(content)` in the app's process.
  - After: `load_user_module(file_path)` uses `importlib.util.spec_from_file_location` and `spec.loader.exec_module(module)` to import the script as a module, with basic validation (exists + `.py` extension) and isolated module namespace. The main code only calls `user_module.run()` if present and callable.
  - Rationale: `exec()` is very dangerous on arbitrary content. `importlib` is still executing code but in a module context with stricter loading semantics and allows easier control/validation. For truly untrusted code, further isolation (container/process/sandbox) is required.

- Removed printing secrets
  - Before: `print(f"Connecting to DB with password: {DB_PASSWORD}")`
  - After: `logging.info("Connecting to DB with provided credentials (hidden)")`
  - Rationale: avoid leaking secrets into logs.

- Added logging, validation, and exception handling to improve observability and safety.

## 7) Explanations for each fix (from highest to lowest severity)

VULN-002 (CRITICAL) — exec() arbitrary code execution
- Fix:
  - Removed `exec(content)`.
  - Added `load_user_module()` which uses `importlib.util.spec_from_file_location` and `spec.loader.exec_module()`.
  - Validates the file exists and has `.py` extension.
- Why this is safer:
  - Avoids executing arbitrary code via exec() in the application global scope.
  - Allows the loaded code to live in its own module namespace and permits validation and explicit callable lookup (`run`).
- Caveat:
  - Importlib still runs code; for untrusted code, run in a separate process/container/sandbox and enforce resource/permission limits.

VULN-001 (HIGH) — hardcoded DB password
- Fix:
  - Removed static `DB_PASSWORD` variable.
  - Now reads from `os.environ.get("DB_PASSWORD")` and raises an exception if missing.
- Why:
  - Prevents credentials from being stored in source control and leaking.
- Recommendation:
  - Use a secrets manager or OS-level secret store (Vault, AWS Secrets Manager, Azure Key Vault) and rotate credentials.

VULN-003 (MEDIUM) — secret printed to logs
- Fix:
  - Replaced prints that revealed secrets with `logging.info` that does not include the password.
- Why:
  - Avoids leaking secrets to logs.
- Recommendation:
  - Use structured logs and redact/hide sensitive fields.

## 8) Edge cases, further improvements & recommendations
- For true isolation of untrusted code:
  - Use containers or separate processes with minimal privileges, chroot/nsjail, seccomp, or sandboxing.
  - Consider running untrusted plugin code only in an API-like interface via RPC to an isolated worker process.
- Secrets management:
  - Integrate with a secrets manager instead of environment variables for production.
  - Add automated scans (git pre-commit hooks, secret scanning) to avoid future leaks.
- Tests:
  - Current tests are static pattern-based. Add unit tests, static analyzers (bandit), and runtime checks as needed.
- Hardening:
  - Add input sanitization, user script signing (only load signed plugin code), and permission restrictions.
